What Is This

An arm64-only, systemless module (Magisk / KernelSU / SUkiSU Ultra) that routes all DNS traffic on the device through dnscrypt-proxy, the open-source DNSCrypt/DoH proxy project, packaged and configured for Android.

The result: your ISP can no longer see or hijack your plaintext DNS queries, and known ad/tracking domains are blocked before a connection to them is even attempted.

03

DNS Flow

App DNS request
↓ iptables redirect (port 53 → 127.0.0.1:5354)
↓ dnscrypt-proxy (encrypted + authenticated)
↓ Cloudflare / Quad9 / Mullvad — fastest resolver wins

Every DNS query on the device is transparently redirected into dnscrypt-proxy via an iptables rule, encrypted, then sent to whichever of the three configured resolvers is currently fastest. Your ISP only ever sees encrypted traffic — never the plaintext domain you're resolving.

ℹ
Android's built-in Private DNS setting is disabled automatically during install. If it stayed on, Android would send queries straight to that DoT server instead, bypassing this module's redirect entirely.
04

IPv6 Handling

IPv6 is disabled at three independent levels simultaneously: Android system properties, kernel sysctl, and an ip6tables policy. The watchdog re-applies this roughly every 60 seconds, so it can't drift back on.

⚠
Because IPv6 is disabled system-wide, anything that specifically depends on it won't function while this module is active.

IPv6-only networks

Some carriers no longer hand out IPv4 at all. On those networks IPv4 traffic is carried inside IPv6 (464XLAT/clat), so blocking IPv6 blocks everything — and rebooting doesn't help, because the block is re-applied on every boot.

The block is still applied unconditionally at boot: at that point the network doesn't exist yet, and guessing permissively is exactly the leak this module prevents. Once the network is up, the watchdog re-checks. If DNS never resolves at all, it lifts the IPv6 block and writes a line to the log explaining why. If resolution is still dead two minutes later, IPv6 wasn't the cause and the block is restored rather than left open.

On a normal IPv4 or dual-stack connection none of this fires — DNS resolves, so nothing is touched.

Turning it off

Settings live in a file that survives module updates:

/data/adb/dnscrypt-proxy-android.conf
IPV6_KILL=1Disable IPv6 entirely (default). Set to 0 to leave IPv6 alone.
QUIC_BLOCK=1Drop outbound UDP/443 so browsers can't bypass the proxy via QUIC's built-in DoH (default). Set to 0 if you need HTTP/3.

Edit, then reboot. Module updates never overwrite this file.

05

Boot Leak Prevention

DNS is blocked at boot until dnscrypt-proxy is confirmed up and listening — there's no window during startup where a query could leak out to the ISP's default resolver before the redirect is in place.

06

Watchdog

A self-healing watchdog monitors dnscrypt-proxy and restarts it automatically if the process crashes or stops, without requiring a reboot or manual intervention.

Blocklists

The dashboard's Update Blocklist button downloads a current OISD/hagezi-based domain list and loads it as blocked-names.txt.

Adding your own domains

To permanently block domains that aren't in the default list — or that keep reappearing after a refresh — edit:

/storage/emulated/0/dnscrypt-proxy/custom-blocked-names.txt

One domain per line, in the suffix-rule format dnscrypt-proxy expects:

*.example.com     # blocks the domain and all subdomains
exact.example.com # blocks only this exact host
# lines starting with # are ignored

Every time you tap Update Blocklist, this file is automatically merged into the freshly downloaded list, deduplicated, and hot-reloaded — no reboot needed. It survives module updates and reflashes, so your custom entries are never lost.

10

IP Encryption (optional)

The [ip_encryption] block in dnscrypt-proxy.toml is a dnscrypt-proxy config option that can encrypt client IP addresses in the query log, using the IPCrypt scheme.

On a phone, every query comes from the device itself — the logged IP is always 127.0.0.1 — so the default algorithm = "none" is correct and there is nothing meaningful to encrypt. This option only becomes relevant if you repurpose dnscrypt-proxy as a shared resolver for other devices on a network, where distinct client IPs would otherwise appear in the log.

  3. If conflicts were removed: reboot, then flash again. If none were found: installation completes in one flash

16

Closing the Gap: ipset-arm64

Notice the last row in the table above — no combination of VPN and DNSCrypt catches an app that connects straight to a hardcoded IP address, skipping DNS resolution entirely. DNSCrypt can only block what it sees a DNS request for; if an app never asks "what's the IP for this domain?" because the IP is baked into its code, DNSCrypt has nothing to intercept.

This is exactly the gap ipset-arm64 — a companion module by the same author — is built to close, using a different mechanism entirely.

DNSCrypt (this module)ipset-arm64
Operates atDNS layerIP / packet layer
Blocks bydomain nameIP address / CIDR range
Stops the connectionbefore an IP is even resolvedafter an IP is known, at the firewall
Blind spotapps with a hardcoded IP, or their own DoH that skips this device's resolverdoesn't know domain names, only addresses — can't tell one hostname on a shared IP from another

Running both gives layered coverage: DNSCrypt blocks known-bad domains cheaply and broadly, before a lookup even happens. ipset-arm64 catches what DNS-level filtering structurally cannot — traffic that never goes through DNS at all.

✓
No conflict between the two modules — DNSCrypt only touches DNS traffic (port 53/853), ipset-arm64 only touches whatever firewall chain/rule you configure in its own WebUI. They don't compete for the same packets.

FAQ

Does it work without a VPN?

Yes, completely independently. The VPN is an optional second layer — DNSCrypt alone already stops ISP DNS surveillance and blocks known ad/tracker domains.

What happens if dnscrypt-proxy crashes?

The self-healing watchdog detects it and restarts the process automatically, without a reboot.

Can I use a custom resolver?

Yes. Edit server_names in dnscrypt-proxy.toml and add any resolver from dnscrypt-proxy's public resolver list. Config changes hot-reload without a reboot.
